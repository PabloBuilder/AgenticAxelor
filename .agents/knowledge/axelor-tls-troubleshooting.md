# Diagnostic TLS Axelor

À consulter lorsqu'un outil MCP signale une erreur de certificat. Ne jamais désactiver la vérification TLS (`NODE_TLS_REJECT_UNAUTHORIZED=0`, `rejectUnauthorized: false`, etc.). Ne pas rejouer automatiquement une écriture : son résultat peut être incertain.

1. Identifier l'environnement avec `list_axelor_sessions` et son URL ; ne pas exposer ni extraire les cookies. Une session active ne garantit pas une connexion valide.
2. Examiner le certificat et la chaîne présentés par le serveur avec `openssl s_client -connect HOTE:443 -servername HOTE -showcerts` ; vérifier les émetteurs, dates et résultat de vérification. Ne transmettre aucun cookie à cette commande. Un certificat expiré, un nom incorrect ou une chaîne manquante exigent des corrections différentes.
3. Privilégier la correction de la chaîne sur le serveur par son administrateur. Ne pas supposer que l'intermédiaire présenté est celui qui manque.
4. Si un intermédiaire manque, obtenir le certificat approprié auprès d'une source officielle fiable ; vérifier son identité, sa chaîne et son empreinte auprès de l'administrateur ou de l'autorité. Ne pas ajouter comme autorité de confiance un certificat fourni par un serveur non vérifié. Ne jamais généraliser le certificat d'une instance à toutes les autres.
5. Pour tester localement sans identifiants, convertir le certificat fiable en PEM si nécessaire, puis démarrer un **nouveau processus Node** avec `NODE_EXTRA_CA_CERTS` pointant vers le fichier PEM et tester une requête HTTPS vers l'URL concernée. Garder la validation TLS active. `NODE_EXTRA_CA_CERTS` est lu au démarrage et ajoute une autorité de confiance : n'utiliser que le certificat vérifié à l'étape 4.
6. Si l'utilisateur a demandé de réparer la connexion ou d'appliquer le correctif, **effectuer directement la configuration locale**, sans lui demander à nouveau de le faire : identifier le fichier de configuration du client MCP effectivement utilisé ; pour Pi dans ce projet, c'est `.pi/mcp.json`. Ajouter `NODE_EXTRA_CA_CERTS` dans `mcpServers.agentic-axelor.env`, avec le chemin absolu vers le PEM vérifié, en conservant les autres paramètres. Cette variable s'applique à toutes les connexions HTTPS de ce processus MCP ; signaler cette portée. Si la demande initiale est seulement un diagnostic ou si le certificat n'est pas vérifié, ne pas modifier la configuration sans autorisation.
7. Redémarrer ou reconnecter le serveur MCP si l'outil le permet. Sinon, informer l'utilisateur que la configuration est faite et lui demander uniquement de redémarrer/reconnecter le MCP dans son client. Si possible, lancer un processus MCP distinct avec la même variable pour tester immédiatement un outil MCP authentifié **en lecture seule**, sur la session ciblée ; préciser que ce test ne prouve pas que le processus MCP actif a été redémarré. Un HTTP 200 sans authentification ne prouve pas que l'API authentifiée fonctionne.
8. Retester ensuite un outil MCP en lecture seule depuis le client actif. Si le problème persiste, signaler l'erreur exacte et solliciter l'administrateur ; ne pas contourner une erreur de nom ou d'expiration en ajoutant des certificats au hasard. Ne pas utiliser le navigateur si l'utilisateur l'a exclu. Si utile et autorisé, le navigateur synchronisé peut servir à une consultation manuelle en lecture seule, sans garantir un contrôle exhaustif.
